# Session log — 2026-09-16

Single session, ~65 minutes, empty `git init` → deployed leaderboard.
Time distribution in [`../time.md`](../time.md).

## The brief

A detailed, post-mortem-informed spec for ranking PostHog engineers on *how* their fix/bug work
landed. It carried hard-won operational knowledge from a previous build that had lost 5,000 PRs
and 90 minutes at 65% completion: guard every `.json()`, build checkpointing first, three
distinct rate limits, byte-stable committed raw, identity is human-reviewed.

The brief was largely right, and where it was wrong it was wrong in ways only measurement could
reveal.

## Phase 1 — Plan (11:11–11:21)

`/plan` was invoked with no arguments against an empty repo, so the first action was to **ask
for the requirement** rather than infer one.

Once the brief arrived, ~10 minutes went to verifying it against the live GitHub API before
writing any code. **Four assumptions failed:**

| Brief said | Measured | Consequence |
|---|---|---|
| Bot exclusion cuts 38% | **8.9%** | The headline speed lever was actually `in:title fix` at −61% |
| Bot list incl. `app/trunk-io` | **0 PRs**; two live bots missing | Exclusion silently weaker than believed |
| RTT ~2.33s | **4.4s** | Latency is 85% of wall-clock — concurrency matters more, pacing less |
| ~7,329 target PRs | **5,945** | Budget projections all shifted |

Two traps were also found in advance:

- **Unedited autonomy templates.** Bodies containing *both* `Fully autonomous` and
  `Human-driven (agent-assisted)` mean the author never filled the field in. A first-match
  parser calls that `human_driven` and misattributes the PR.
- **`in:title fix` is already precise here** (100/100 sampled titles matched the
  conventional-commit prefix), so the client-side regex became a logged assertion rather than a
  filter that silently drops rows.

Confirmed as briefed: `bugfix`/`hotfix` both 0, `label:bug` useless at 25, 0.56 points/PR,
median 2 files/PR, autonomy template coverage high.

## Phase 2 — Implement (11:21–11:47)

Built in the plan's order, which put **checkpointing before any long fetch**. The acceptance
test — `kill -9` mid-run, resume, assert zero duplicates and zero loss — was written and passing
before the first real download. That decision paid off within the hour.

Order: scaffold → checkpoint + byte-stable raw → client + limiter → pagination → identity +
autonomy → skim + hydrate → schema → metrics → scoring → serving → UI → Docker.

### Deviations found by measuring

**`checkSuites` is empty on this repo.** The plan specified
`checkSuites(first:5){nodes{conclusion}}`. It returns only stale QUEUED suites with **null
conclusions** — so `ci_first_pass_rate`, a scored metric, was silently always `None`. No error,
no warning.

`statusCheckRollup` reports real state, but requesting it across all 30 commits costs **3.22s
per 25-PR batch versus 0.88s for the first commit alone**, at identical point cost. Since
`ci_first_pass_rate` is defined on the *first pushed commit* anyway, the rollup is now requested
on exactly two commits. Combined with raising the comments page from 10 to 30 (12 of 14 overflow
drains were comments), hydration went **1.15s/PR → 0.30s/PR**.

**`weekend_activity_share` was dropped on principle** — surfacing weekend work in a ranking tool
invites precisely the misuse the caveats panel warns against.

## Phase 3 — Production run (11:49–12:05)

Skim: 5,945 PRs in 3m30s. Confirmed the bot share live at **8.9%**, matching planning and not
the brief's 38%.

Hydrate leg 1 reached 4,000/5,136 and **stalled**.

### Bug 1 — concurrency cascade

```
11:59:46  throttled; concurrency halved -> 4
11:59:47  throttled; concurrency halved -> 2
11:59:48  throttled; concurrency halved -> 1
```

A single 403 burst was reported independently by every in-flight worker, each halving. With
`clean_window=20`, recovery needed 20 clean requests per step, so the run crawled rather than
failing — nothing errored, which is what made it dangerous.

Fixed with a 15s cooldown (longer than worst-case RTT) so one *episode* halves once. The restart
then exercised resume for real:

```
resuming hydrate: 4000 done, 1136 remaining
```

Zero refetch, zero duplicates, checkpoint intact through a mid-run kill. The post-fix leg climbed
to concurrency 7 with **no halving at all**.

**Final:** 5,136 PRs, ~1,550 of 5,000 points (one window), 0 backoffs, 0 data loss, **77 transient
errors absorbed** — 55 GitHub 502/504s and 4 truncated JSON-200 bodies. The `.json()` guard the
brief insisted on fired on genuinely truncated payloads, not just HTML error pages.

## Phase 4 — Scoring (12:05–12:16)

### Bug 2 — tie bands chained transitively

All 50 people landed in one band. Rank 1 `[0.637,0.766]` and rank 50 `[0.051,0.368]` plainly do
not overlap, yet shared a band.

Tracking a running *minimum* of `ci_low` chains transitively (A~B, B~C ⇒ one band), and on any
smooth distribution that collapses to a single meaningless band. Fixed by anchoring on the band
leader's lower bound → **3 real bands**.

### `revert_rate` demoted

Only 23 revert-titled PRs in the corpus, and **1 of 50 people nonzero**. The other 49 shared an
identical percentile, so it added a constant to every score — no separation — while consuming
6.45% of the weight and diluting metrics that do discriminate. It failed the plan's own second
selection criterion ("separates people rather than clustering them").

Demoted to context-only. Its weight renormalised within Builder (`test_habit` 13.95→16.28%,
`risk_weighted_contribution` 11.7→13.66%). Weights were simultaneously restructured from
hand-tuned absolute constants into **within-pillar shares with absolutes derived**, so demoting
anything rebalances exactly instead of silently leaving the pillar short.

## The headline result

`Gilbert09` authored **1,285 PRs in 90 days — 1,160 of them (90.3%) self-declared fully
autonomous**, almost exactly the 91% the brief predicted. First by a wide margin on every volume
metric; **#27, band 2** here, scored on the 125 PRs actually authored rather than the 1,160
dispatched, with `dispatched_n=1160` displayed rather than hidden.

That is the thesis of the whole exercise reproducing itself on real data.

## What the tests caught vs. what production caught

Worth recording honestly: **both real bugs were found by looking at production output, not by
the 111 tests.** The tests caught expectation errors and regressions; they did not anticipate
a throttle-report storm or a transitive-closure bug in banding.

What the tests *did* guarantee was that fixing both was safe and fast — and that resume worked
when the first bug killed a run at 78% completion, turning a 9-minute re-download into a
15-second restart.
